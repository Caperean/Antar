Project Assumptions – Renderer 2D + WebGPU (Antar Engine)
[Updated after adding fillPolygon() — changes marked with >>> ]
(Previously: zalozenia.txt — Polish version)

1. Division into two modules: Renderer2D (CPU) and GpuContext (GPU)
The project intentionally separates rendering logic from GPU backend:

Renderer2D (CPU):
does not know WebGPU

does not have device, queue, surface

does not manage GPU textures

does not execute draw calls

operates only on Rust structures

collects commands (DrawCommand)

processes transforms (translate/rotate/scale)

maintains state (RenderState)

generates instances (sprite, rect, >>> polygon) ready to send to GPU

GpuContext (GPU backend):
the only place that knows WebGPU

has device, queue, surface, swapchain

manages GPU textures (TextureHandle → GpuTexture)

has pipelines, buffers, bind groups

executes draw calls

renders instances generated by Renderer2D

>>> also stores global rendering configuration unrelated to
>>> any single instance (see point 2b)

Renderer2D = 2D logic
GpuContext = GPU execution

Status: CURRENT without reservations. fillPolygon() fully respects this
division — resolve_fill_polygon() in Renderer2D does not import web_sys and does
not know anything about WebGPU; all new GPU infrastructure (storage buffers,
dummy texture, bind groups) lives exclusively in GpuContext.

2. Command architecture (Command Buffer)
All drawing operations are recorded as commands:

DrawCommand::DrawImage
DrawCommand::FillRect
>>> DrawCommand::FillPolygon
DrawCommand::Clear
DrawCommand::SetFillStyle
DrawCommand::SetAlpha
DrawCommand::Transform(...)
DrawCommand::PushState
DrawCommand::PopState

Renderer2D does not draw immediately.
Instead:

JS calls API (e.g. drawImage, fillRect, translate)

Antar parses parameters from JsValue

Renderer2D adds command to queue

present() retrieves all commands

GpuContext executes them on GPU

This enables batching, instancing, transforms, and optimizations.

Status: CURRENT for drawing operations. fillPolygon() goes through
exactly the same cycle (JS → from_js → DrawCommand → present() →
GpuContext).

>>> 2b. Third category of operations: global renderer configuration
>>> (outside command model)
>>>
>>> Not every public Antar method goes into the command queue. From the
>>> beginning there was already a second category — resource management
>>> (loadTexture / unloadTexture) — which writes directly to GpuContext,
>>> bypassing DrawCommand, because it's not a "draw something in this frame"
>>> operation, but resource state management.
>>>
>>> fillPolygon() added four more representatives of this category:
>>>
>>>   setDebugMode(mode)
>>>   setOutputGamma(gamma)
>>>   setMinPolygonAreaPx(px)
>>>   setEdgeSoftness(px)
>>>
>>> These methods set fields directly on GpuContext (self.gpu.debug_mode
>>> = mode, etc.), they don't create DrawCommand. Justification: this is
>>> global rendering configuration (affects every subsequent fillPolygon(),
>>> not assigned to a single drawing instance), not a spatial drawing
>>> operation.
>>>
>>> Updated division of Antar operations into three categories:
>>>   a) Drawing operations → DrawCommand → queue → present()
>>>      (clear, fillRect, fillPolygon, drawImage, transforms, save/restore)
>>>   b) Resource management → directly to GpuContext
>>>      (loadTexture, unloadTexture, createTextureAtlas)
>>>   c) Global renderer configuration → directly to GpuContext
>>>      (setDebugMode, setOutputGamma, setMinPolygonAreaPx, setEdgeSoftness)

3. Drawing parameters passed as JS objects → Rust
wasm-bindgen cannot pass complex Rust structures.
Therefore API accepts JsValue, then manually parses:

RectDrawParams::from_js()

ImageDrawParams::from_js()

>>> PolygonDrawParams::from_js()

Color::from_js()

Rect::from_js()

JS sends plain objects:

js
Renderer.drawImage({
    texture: 1,
    src: { x: 0, y: 0, w: 32, h: 32 },
    dst: { x: 100, y: 200, w: 64, h: 64 },
    rotation: 0,
    color: { r: 1, g: 1, b: 1, a: 1 }
});

>>> Renderer.fillPolygon({
>>>     points: [x0, y0, x1, y1, x2, y2, ...], // flat list, min. 3 vertices
>>>     color: { r: 1, g: 1, b: 1, a: 1 },       // optional, default white
>>>     renderMode: "fill" | "outline" | "mask", // optional, default "fill"
>>>     outlineWidth: 4,                          // px, only OUTLINE
>>>     texture: texId,                           // optional, only FILL
>>>     skipIfTransparent: false                  // optional performance hint
>>> });

Rust converts this to pure structures.

Status: CURRENT, pattern unchanged — just one more variant added.

4. Textures – full CPU/GPU separation
Renderer2D does not have GPU textures.
It only knows:

TextureHandle(u32)

Real WebGPU textures are stored in GpuContext.

Loading texture:

Antar.loadTexture() → GpuContext.load_texture()

Unloading texture:

Antar.unloadTexture() → GpuContext.unload_texture()

Renderer2D sees only texture ID.

>>> fillPolygon() introduces one new nuance: texture is OPTIONAL for it
>>> (only FILL mode uses it; OUTLINE and MASK never sample textures —
>>> this is a conscious decision from the original SDF algorithm).
>>> Lack of texture is signaled by the existing convention TextureHandle(0)
>>> = "no/invalid texture" (TextureRegistry reserves it from the start).
>>> GpuContext then binds an internal 1x1 white pixel dummy texture —
>>> Renderer2D still knows nothing about this detail, it just sees
>>> Option<TextureHandle>.

Status: CURRENT, separation maintained. Texture optionality is an
extension of the pattern, not a violation.

5. 2D Transforms (Canvas-style, but correct)
Transforms are commands:

TransformOp::Translate
TransformOp::Rotate
TransformOp::Scale
PushState
PopState

Renderer2D maintains a transform stack and current matrix.

>>> CHANGE: "GPU backend gets the ready matrix in the instance" — this
>>> sentence is true ONLY for SpriteInstance and RectInstance.
>>>
>>> For PolygonInstance it's different: transform is applied to EVERY
>>> VERTEX on CPU, in resolve_fill_polygon(), ONCE, before upload —
>>> PolygonInstance doesn't contain a transform field at all. On GPU
>>> it receives already transformed world/screen coordinates.
>>>
>>> Conscious decision, not drift: SDF per-pixel in fragment shader is
>>> the only part of the algorithm that actually pays off to keep in WGSL;
>>> transforming a handful of polygon vertices (once per fillPolygon call,
>>> not once per pixel) is cheap and gains nothing from moving to shader
>>> — and eliminates the need to pass a matrix and calculate it per-pixel
>>> in the SDF loop.
>>>
>>> Updated sentence: "GPU backend gets either a ready matrix in the
>>> instance (sprite/rect), or already transformed geometry (polygon) —
>>> depending on what's cheaper for that instancing shape."

---

6. Instancing and batching
Renderer2D generates structures:

SpriteInstance
RectInstance
>>> PolygonInstance

>>> CHANGE: description "Each instance contains: transform matrix, color,
>>> alpha, UV, texture ID" matched SpriteInstance. RectInstance already
>>> partially broke it (no UV/texture). PolygonInstance breaks it more:
>>>
>>>   - NO transform field (see point 5)
>>>   - NO stored UV (calculated in shader from dst, not in buffer)
>>>   - ADDS vertex_offset/vertex_count (geometry is not a constant quad,
>>>     but variable number of points in separate storage buffer)
>>>   - ADDS render_mode, outline_width, texture_id (Option),
>>>     skip_if_transparent — fields the original assumptions didn't
>>>     predict at all
>>>
>>> Updated sentence: "Instance data shape depends on drawing type — not
>>> every instance type carries the same field set. Sprite and rect share
>>> the 'constant quad + matrix' pattern; polygon has the 'variable
>>> geometry in separate buffer + AABB + mode metadata' pattern."

GpuContext batches instances by texture and pipeline.

>>> For polygon batching is two-level: by pipeline (polygon ≠
>>> sprite ≠ rect) and within polygon pipeline — by texture_id,
>>> exactly like sprite (consecutive runs of the same texture handle =
>>> one draw call).

Atlas is generated on CPU:

packing sprites

generating UV

combining pixels into one texture

Upload atlas → GpuContext.load_texture().

Status: CURRENT unchanged. fillPolygon() doesn't touch the atlas.

8. JS API – simple and consistent
API is modeled on Canvas2D, but operates on commands:

Renderer.clear("#000")
Renderer.setFillStyle("#fff")
Renderer.setGlobalAlpha(0.5)
Renderer.translate(10, 20)
Renderer.rotate(Math.PI / 4)
Renderer.drawImage({...})
Renderer.fillRect({...})
>>> Renderer.fillPolygon({...})
Renderer.present()

>>> Global renderer configuration (category c from point 2b) — outside
>>> Canvas2D model, because Canvas2D has no equivalent (SDF debug/gamma/
>>> culling are concepts outside standard Canvas API):
>>> Renderer.setDebugMode(0)
>>> Renderer.setOutputGamma(2.2)
>>> Renderer.setMinPolygonAreaPx(1.0)
>>> Renderer.setEdgeSoftness(1.5)

9. Project goals
clean architecture

full logic/GPU separation

easy testing of Renderer2D without WebGPU

easy addition of new backends (e.g. WebGL)

easy addition of new drawing types

performance thanks to batching and instancing

JS/TS-friendly API

Status: CURRENT. "Easy addition of new drawing types" was tested in
practice by fillPolygon() — a new instance type with different data
shape than sprite/rect could be added without changing existing types'
architecture.
